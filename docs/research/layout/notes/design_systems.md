Retrieval notes (apply to the whole file):

Material 3 facts below come from Google-owned secondary primaries: the Angular Material theming guide, the `material-web` token source, and Android developer docs. Anything I could not confirm there is listed under Gaps.

## Material 3: density scale, spacing/grid, layout regions and panes, card guidance, type scale for display numbers

### Takeaway
Material's density is one integer knob (0 down to negative values) where each step removes 4px from affected component sizes; it is meant for components that compete for layout space (tables, lists, form fields), not for pop-up/task surfaces, and Google's own Angular docs warn that anything below 0 can hurt accessibility. Layout is driven by window-size classes (600 / 840 / 1200 / 1600) and panes rather than a fixed column grid, and the type scale gives a ready-made ladder for KPI numbers (Display 36/45/57, Headline 24/28/32).

### Cited Findings
- Angular Material's `mat.theme` density "accepts integers from 0 to -5, where 0 is the default spacing and -5 is the most dense and compact layout. Each whole number step down (-1, -2, etc.) reduces the affected sizes by 4px, down to the minimum size necessary for a component to render itself coherently." — [Angular Material theming guide](https://github.com/angular/components/blob/main/guides/theming.md)
- "Setting the density below 0 can reduce accessibility and make navigation harder for users of assistive technology." — [Angular Material theming guide](https://github.com/angular/components/blob/main/guides/theming.md)
- "Density customizations do not affect components that appear in task-based or pop-up contexts, such as the date picker. The Material Design density guidance explicitly discourages changes to density for such interactions because they don't compete for space in the application's layout." — [Angular Material theming guide](https://github.com/angular/components/blob/main/guides/theming.md)
- Density is set as one value in the theme map and emitted as CSS variables alongside color and typography: `@include mat.theme((color: mat.$violet-palette, typography: Roboto, density: -2))`. — [Angular Material theming guide](https://github.com/angular/components/blob/main/guides/theming.md)
- Material's density scale starts at 0 (default) and moves to negative numbers (-1, -2, -3) as space decreases; each increment decreases component height by 4dp; worked web example for a button: 36px + 4px × (-3) = 24px. (Search-result summaries of the M2 "Applying density" page and Google Design's article; the pages themselves would not render for me.) — [Applying density (M2)](https://m2.material.io/design/layout/applying-density.html); [Using Material Density on the Web](https://medium.com/google-design/using-material-density-on-the-web-59d85f1918f0)
- Window size classes (width): Compact < 600dp; Medium 600–839dp; Expanded 840–1199dp; Large 1200–1599dp; Extra-large ≥ 1600dp. Large and extra-large were added "to better target desktop and connected displays." — [Android: Use window size classes](https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes)
- Height classes: Compact < 480dp; Medium 480–899dp; Expanded ≥ 900dp. "Available width is usually more important than available height due to the ubiquity of vertical scrolling"; when height is compact, "two pane layouts are not practical." — [Android: Use window size classes](https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes)
- Recommended workflow: with a compact layout in hand, "first optimize your layout for the expanded width size class ... Then decide what layout makes sense for the medium width size class." — [Android: Use window size classes](https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes)
- Google's adaptive-layout codelab (M3 Design Kit): expanded layout uses a 12-column grid; a pane is "a grouping within the body region"; containment can be implicit (white space) or explicit (dividers, cards, a surface-container color role); feed cards are spaced 24dp apart; detail-pane padding is 16dp; 24dp of space under a header group acts as an implicit boundary; body text capped at about 60 characters per line; the three canonical layouts are Feed, List-Detail and Supporting Pane; bottom navigation becomes a navigation rail at medium/expanded. — [Design an Adaptive Layout with Material Design (codelab)](https://developer.android.com/codelabs/adaptive-material-guidance)
- Same codelab, type on large screens: page title uses Display Large, detail-pane title uses Display Small, other text Body Medium/Large. — [Design an Adaptive Layout with Material Design (codelab)](https://developer.android.com/codelabs/adaptive-material-guidance)
- M3 type scale token values (font-size / line-height, from the `material-web` token source): Display L 57/64, M 45/52, S 36/44; Headline L 32/40, M 28/36, S 24/32; Title L 22/28, M 16/24, S 14/20; Body L 16/24, M 14/20, S 12/16; Label L 14/20, M 12/16, S 11/16. — [material-web `_md-sys-typescale.scss`](https://github.com/material-components/material-web/blob/main/tokens/versions/latest/sass/_md-sys-typescale.scss)
- Weights in that scale: Display, Headline, Body and Title Large are regular (400); Title Medium/Small and all Labels are medium (500); Label Large/Medium have a "prominent" bold variant. Tracking is negative only on Display Large (-0.25px) and positive on small text (Label M/S +0.5px, Body S +0.4px). — [material-web `_md-sys-typescale.scss`](https://github.com/material-components/material-web/blob/main/tokens/versions/latest/sass/_md-sys-typescale.scss)
- Type tokens are exposed as CSS custom properties named `--md-sys-typescale-<scale>-<size>-<property>` with four properties per style (font, size, line-height, weight); each role has three sizes. — [material-web typography docs](https://github.com/material-components/material-web/blob/main/docs/theming/typography.md)

### Inferences
- For a hotel KPI tile, M3's scale suggests: value in Display Small (36/44) or Headline Large/Medium (32/40, 28/36) at regular weight; tile label in Label Large/Medium (14/20 or 12/16, weight 500); delta/caption in Body Small (12/16). Hierarchy comes from size, with weight staying at 400–500. M3 does not publish a "dashboard number" style; this mapping is my reading of the scale.
- The 4px-per-step rule maps cleanly onto row/control heights: e.g. a 48 → 44 → 40 → 36 ladder for table rows, driven by one integer.
- The "don't densify pop-up/task surfaces" rule translates to: density mode should change tables, lists, filters and card padding, but leave dialogs, date-range pickers and menus alone.
- Pane/window-class thinking suits a dashboard with a side panel (e.g. an AI assistant): one pane below 840px, two panes from 840px, optionally three from 1600px.

### Gaps
- Could not read m3.material.io directly, so these official M3 specifics are unverified: pane spacer value (commonly cited as 24dp), fixed-pane widths (commonly cited as 360dp), margins per window class (a third-party SAP Fiori page says 16dp compact / 24dp medium and expanded, but that is SAP's adaptation), and whether M3's layout page still states a density scale explicitly or leaves it to component specs.
- No verified M3 card spec values (padding, corner radius, elevated vs filled vs outlined usage rules) were retrieved.
- A search summary attributed the statement "the more dense your components become, the larger your margins and gutter widths should be" to Material-era guidance but did not make clear which page it came from; unverified.
- M3 Expressive (2025) changes to spacing/typography ("emphasized" type styles exist in the token folder) were not examined.

## IBM Carbon: 2x grid, spacing tokens, productive vs expressive type and motion, data table densities, dashboard/data-viz guidance

### Takeaway
Carbon is the most explicit system for data-heavy products: an 8px "mini unit", a 13-step spacing scale (2–160px), three gutter modes (32 / 16 / 1px) with condensed 1px gutters named specifically for dashboards, five table row heights (24/32/40/48/64) that all keep 14px text, and a "productive" type and motion set reserved for task-focused UI. Density is achieved by changing row height and gutter, not by shrinking type.

### Cited Findings
- Spacing scale: `$spacing-01` 2px, `-02` 4px, `-03` 8px, `-04` 12px, `-05` 16px, `-06` 24px, `-07` 32px, `-08` 40px, `-09` 48px, `-10` 64px, `-11` 80px, `-12` 96px, `-13` 160px. Built on multiples of two, four and eight. — [Carbon: Spacing](https://carbondesignsystem.com/elements/spacing/overview/)
- Small increments suit individual components and larger increments control a design's density; "deviating from the spacing scales should be avoided whenever possible." — [Carbon: Spacing](https://carbondesignsystem.com/elements/spacing/overview/)
- Tokens do not change with screen size; instead step up or down the scale at breakpoints (example given: `$spacing-05` at 1440px becoming `$spacing-03` at 768px). — [Carbon: Spacing](https://carbondesignsystem.com/elements/spacing/overview/)
- Proximity and hierarchy: closer elements read as more related; repeating a spacing pattern signals equal weight; space can group content without dividers; more surrounding space signals higher importance. Dense sections are acceptable but "there should be white space to let the user's eye rest." — [Carbon: Spacing](https://carbondesignsystem.com/elements/spacing/overview/)
- 2x Grid: the basic unit is an 8px square ("mini unit"); columns, rows, boxes, margins and padding are multiples of it; the grid divides or multiplies by two. Fixed sizing scale: 8, 16, 24, 32, 48, 64, 80px. — [Carbon: 2x Grid overview](https://carbondesignsystem.com/elements/2x-grid/overview/)
- Breakpoints and columns: sm 320px (4 col), md 672px (8 col), lg 1056px (16 col), xlg 1312px (16 col), max 1584px (16 col). Padding is 16px at every breakpoint; margins 0 / 16 / 16 / 16 / 24px. — [Carbon: 2x Grid overview](https://carbondesignsystem.com/elements/2x-grid/overview/)
- Box aspect ratios to prefer: 1:1, 2:1, 2:3, 3:2, 4:3, 16:9. — [Carbon: 2x Grid overview](https://carbondesignsystem.com/elements/2x-grid/overview/)
- Gutter modes: Wide = 32px (default; for separate destinations or text-heavy layouts); Narrow = 16px (containers hang 16px into the gutter, type stays on columns; "the most common mode in product implementation"); Condensed = 1px (tiles get a 1px `$border-subtle` border; for "pieces of information that form a larger picture, such as dashboards, overview pages, portals, and resource tiles"). — [Carbon: 2x Grid usage](https://carbondesignsystem.com/elements/2x-grid/usage/)
- Type never hangs into the gutter in any mode; mixing gutter modes is "the rule rather than the exception"; labeled fixed components (inputs, dropdowns) must use the wide mode. — [Carbon: 2x Grid usage](https://carbondesignsystem.com/elements/2x-grid/usage/)
- High-density interface model: uses full browser width and adds columns in increments of two; suited to complex product interfaces, catalogs and data-visualization dashboards; dense data visualizations use fixed spacers (the mini-unit grid) instead of fluid columns. — [Carbon: 2x Grid usage](https://carbondesignsystem.com/elements/2x-grid/usage/)
- Grid influencers: opening a left nav keeps the column count and resizes columns fluidly; a slide-in side panel resizes content and reduces the number of columns. — [Carbon: 2x Grid usage](https://carbondesignsystem.com/elements/2x-grid/usage/)
- Data table row heights: xs 24px, sm 32px, md 40px, lg 48px, xl 64px. All use `body-compact-01` (14px, 400) for row text and `heading-compact-01` (14px, 600) for column headers; header row must match row size. — [Carbon: Data table style](https://carbondesignsystem.com/components/data-table/style/)
- When to use each: xs for highly dense layouts where "maximizing information within limited space is a priority"; sm for compact interfaces that still need comfortable readability; md is the default and most common; lg for spacious layouts where easier interaction and emphasis matter; xl only when rows are expected to hold two lines of content. — [Carbon: Data table usage](https://carbondesignsystem.com/components/data-table/usage/)
- Toolbar, batch-action bar and pagination heights must match the row height (small toolbar 32px with xs/sm; large 48px with lg/xl). Row hover should always be enabled to help scanning across columns; zebra stripes aid horizontal scanning; give the table the most width on the page and avoid nesting it in small containers. — [Carbon: Data table usage](https://carbondesignsystem.com/components/data-table/usage/)
- Productive vs expressive type: productive (suffix `-01`) is for product interfaces, condensed and task-focused, with fixed heading sizes; expressive (`-02`) is for editorial/marketing, larger, with responsive headings; expressive styles would be "distracting if used in product." — [Carbon: Typography overview](https://carbondesignsystem.com/elements/typography/overview/)
- Type scale formula from a 12px base: Xn = Xn-1 + {INT[(n-2)/4] + 1} × 2, giving 12, 14, 16, 18, 20, 24, 28, 32, 36, 42, 48, 54, 60, 68, 76, 84, 92px. — [Carbon: Typography overview](https://carbondesignsystem.com/elements/typography/overview/)
- Productive tokens (size/line-height, weight): `label-01` and `helper-text-01` 12/16, 400, +0.32px tracking; `body-compact-01` 14/18, 400; `body-01` 14/20, 400; `heading-compact-01` 14/18, 600; `heading-01` 14/20, 600; `heading-03` 20/28, 400; `heading-04` 28/36, 400; `heading-05` 32/40, 400; `heading-06` 42/50, 300; `heading-07` 54/64, 300. — [Carbon: Type sets](https://carbondesignsystem.com/elements/typography/type-sets/)
- Compact line heights (`body-compact-01`, 14/18) are for short paragraphs of no more than four lines, typically inside components; `body-01` (14/20) is for longer text; compact headings pair with compact body. — [Carbon: Type sets](https://carbondesignsystem.com/elements/typography/type-sets/)
- Productive motion is subtle and efficient, for task moments (button states, dropdowns, rendering data tables); expressive motion is for significant, occasional moments (opening a page, primary action, system alerts). — [Carbon: Motion](https://carbondesignsystem.com/elements/motion/overview/)
- Easing (productive / expressive): standard `cubic-bezier(0.2, 0, 0.38, 0.9)` / `(0.4, 0.14, 0.3, 1)`; entrance `(0, 0, 0.38, 0.9)` / `(0, 0, 0.3, 1)`; exit `(0.2, 0, 1, 0.9)` / `(0.4, 0.14, 1, 1)`. — [Carbon: Motion](https://carbondesignsystem.com/elements/motion/overview/)
- Duration tokens: fast-01 70ms, fast-02 110ms, moderate-01 150ms, moderate-02 240ms, slow-01 400ms, slow-02 700ms; duration should scale with distance/size of change; provide reduced-motion alternatives. — [Carbon: Motion](https://carbondesignsystem.com/elements/motion/overview/)
- Dashboards: two types, presentation (KPI status, big picture) and exploration (interactive: filter, sort, drill down). Rank data by importance, giving the most important data the highest contrast and largest area; put it at the top and follow an F-shaped reading pattern; limit the number of metrics; use the same color for each data set throughout; give all charts the same layout and spacing and keep legends in the same position; linked charts should mirror filters and zoom. — [Carbon: Dashboards](https://carbondesignsystem.com/data-visualization/dashboards/)
- The dashboards page cites research claiming white space improves comprehension by almost 20 percent (it does not link the underlying study in the text I retrieved). — [Carbon: Dashboards](https://carbondesignsystem.com/data-visualization/dashboards/)

### Inferences
- Carbon's model for a dashboard is: tight separation between tiles (1px condensed or 16px narrow gutter), 16px padding inside every tile, and generous space reserved for a few places (page header, KPI band). "Airiness" comes from consistent inner padding and hierarchy, not from wide gaps between every tile.
- Because all five row sizes keep 14px text, a density toggle in a table should change only row height (and matching toolbar/pagination height), keeping type constant. That keeps the type scale theme-independent.
- The KPI number in Carbon terms would be `heading-05`/`-06` (32/40 or 42/50, light-to-regular weight) with a `label-01` (12/16) caption; Carbon's large headings deliberately drop to weight 300–400.
- Productive motion for a dashboard means 70–150ms transitions for hovers, filter changes and table re-renders; 240–400ms only for panel expansions.

### Gaps
- The Carbon dashboards page gives no numeric rules for chart sizes, tile padding, or number of charts per view; those had to be taken from the grid/spacing pages.
- I did not retrieve Carbon's `Layout`/size-density component tokens (`--cds-layout-size-height-*`, `--cds-layout-density-padding-inline-*`), so how Carbon v11 wires density through CSS custom properties is not confirmed here.
- Per-row-size cell padding values for the data table are not stated on the style page (only that xl offsets content with 16px top padding).
- Carbon gives no guidance on numeric column alignment on the pages retrieved.

## Apple HIG: layout, spacing, typography hierarchy, charts guidance

### Takeaway
Apple gives principles rather than a spacing scale: order by importance from top-leading, align for scanning, group with negative space or container shapes, and use progressive disclosure instead of packing everything in. Its macOS text styles are a useful dense-desktop reference (13pt body, 10pt minimum, 26pt largest title), and its chart guidance insists on a summary headline per chart, data as the most prominent layer, and consistency across related charts.

### Cited Findings
- "Order content by relative importance ... place the most important items near the top and leading side of the window or display." — [Apple HIG: Layout](https://developer.apple.com/design/human-interface-guidelines/layout)
- "Align elements to make them easier to scan, and use indentation to convey hierarchy ... People assume that aligned items are related to each other." — [Apple HIG: Layout](https://developer.apple.com/design/human-interface-guidelines/layout)
- "Group related items to clearly express related information or functions. For example, you might use negative space, container shapes, or separator lines to show which elements are related and which are unrelated." — [Apple HIG: Layout](https://developer.apple.com/design/human-interface-guidelines/layout)
- "Use progressive disclosure to make layouts cleaner and easier to interact with. An interface with too much content and too many choices makes it harder to find information quickly." — [Apple HIG: Layout](https://developer.apple.com/design/human-interface-guidelines/layout)
- Keep functionality the same as the available space changes; change how much is visible, e.g. switch from a tab bar to a sidebar in larger spaces. On macOS, avoid placing controls or critical information at the bottom of a window. — [Apple HIG: Layout](https://developer.apple.com/design/human-interface-guidelines/layout)
- Default and minimum text sizes: macOS 13pt default / 10pt minimum; iOS and iPadOS 17pt / 11pt. Avoid Ultralight, Thin and Light weights, especially at small sizes. — [Apple HIG: Typography](https://developer.apple.com/design/human-interface-guidelines/typography)
- macOS built-in text styles (size/line height in points): Large Title 26/32; Title 1 22/26; Title 2 17/22; Title 3 15/20; Headline 13/16 bold; Body 13/16; Callout 12/15; Subheadline 11/14; Footnote 10/13; Caption 1 10/13; Caption 2 10/13 medium. — [Apple HIG: Typography](https://developer.apple.com/design/human-interface-guidelines/typography)
- "Adjust font weight, size, and color as needed to emphasize important information and help people visualize hierarchy"; minimize the number of typefaces. — [Apple HIG: Typography](https://developer.apple.com/design/human-interface-guidelines/typography)
- Tight leading can help text fit in height-constrained areas such as list rows, but "if you need to display three or more lines of text, avoid tight leading even in areas where height is limited"; loose leading suits wide columns and long passages. — [Apple HIG: Typography](https://developer.apple.com/design/human-interface-guidelines/typography)
- SF Pro tracking is size-specific: positive at small sizes (e.g. +0.12pt at 10pt), zero at 12pt, negative through the text range (e.g. -0.43pt at 17pt), and slightly positive again from about 24pt upward. — [Apple HIG: Typography](https://developer.apple.com/design/human-interface-guidelines/typography)
- Charts: "Establish a consistent visual hierarchy ... you want the data itself to be most prominent, while letting the descriptions and axes provide additional context without competing with the data." — [Apple HIG: Charts](https://developer.apple.com/design/human-interface-guidelines/charts)
- "Summarize the main message of your chart" with a title and subtitle so people grasp it without examining details (Weather's precipitation headline is the example). — [Apple HIG: Charts](https://developer.apple.com/design/human-interface-guidelines/charts)
- In compact environments, maximize plot-area width: keep vertical-axis labels as short as possible, describe units in the title instead. — [Apple HIG: Charts](https://developer.apple.com/design/human-interface-guidelines/charts)
- "Align a chart with surrounding interface elements"; to keep a clean leading edge, consider placing the Y axis on the trailing side so tick labels don't protrude past the chart's leading edge. — [Apple HIG: Charts](https://developer.apple.com/design/human-interface-guidelines/charts)
- Grid lines: "Too many grid lines can be visually overwhelming ... too few grid lines can make it difficult to estimate a mark's value"; if a chart is interactive, use fewer grid lines and lighter label colors. Prefer familiar tick sequences (0, 5, 10). — [Apple HIG: Charts](https://developer.apple.com/design/human-interface-guidelines/charts)
- Axis ranges: use a fixed range when min/max are meaningful (0–100%); a zero lower bound suits bar charts, but can hide meaningful differences in other charts (heart-rate example). — [Apple HIG: Charts](https://developer.apple.com/design/human-interface-guidelines/charts)
- Let people interact, "but don't require interaction to reveal critical information"; do not rely on color alone; add visual separation between contiguous areas of color. — [Apple HIG: Charts](https://developer.apple.com/design/human-interface-guidelines/charts)
- "Keep a chart simple, letting people choose when they want additional details. Resist the temptation to pack as much data as possible into a chart." Not every data set needs a chart; a sortable list or table may serve better. — [Apple HIG: Charting data](https://developer.apple.com/design/human-interface-guidelines/charting-data)
- "Match the size of a chart to its functionality, topic, and level of detail"; a small chart works for glanceable information or as a preview of a larger version. — [Apple HIG: Charting data](https://developer.apple.com/design/human-interface-guidelines/charting-data)
- "Prefer consistency across multiple charts, deviating only when you need to highlight differences"; when several charts show the same data set, use one chart type and consistent colors, annotations, layouts and descriptive text (Health Trends small charts expand into the same style). — [Apple HIG: Charting data](https://developer.apple.com/design/human-interface-guidelines/charting-data)

### Inferences
- Apple's macOS ladder shows a desktop data UI can be legible with a narrow range (10–26pt) if weight and color carry hierarchy; on the web, 12px is a safer floor than 10–11px because the macOS sizes assume SF Pro with optical sizing.
- "Summary headline + chart" maps directly to a card pattern: card title, one-line takeaway or headline number, then the plot. This also satisfies the "don't require interaction" rule.
- Sparkline-in-KPI-tile and full chart in a detail view should share color, mark type and annotations (Health Trends rule).

### Gaps
- Apple publishes no numeric spacing scale or grid for apps in the HIG pages retrieved (only platform safe-area margins such as tvOS 60/80pt), so no token values can be attributed to Apple.
- The HIG has no dashboard-specific page; the charts guidance was written for native apps (Swift Charts) and is applied to web by analogy.
- The HIG pages I read mention a Liquid Glass material in the Layout page; I did not research how it affects density or spacing.

## Shopify Polaris, Atlassian, GitHub Primer

### Takeaway
All three use a 4px-based scale with semantic aliases on top. Polaris states the clearest dashboard-relevant doctrine ("the admin is high density by default"; 16px card padding and card gap; 6px table cell padding; dividers only inside tables), Atlassian supplies the clearest usage bands (0–8px inside components, 12–24px between elements, 32–80px between page sections) plus a strict flat-first elevation model, and Primer ships density as named token variants (`condensed` / `normal` / `spacious`).

### Cited Findings

Polaris (React-era docs and tokens in the GitHub repo):
- Space tokens are named as a percentage multiplier of a 4px base: `space-100` = 4px, `space-400` = 16px. Scale: 0, 1 (`025`), 2 (`050`), 4 (`100`), 6 (`150`), 8 (`200`), 12 (`300`), 16 (`400`), 20 (`500`), 24 (`600`), 32 (`800`), 40 (`1000`), 48 (`1200`), 64 (`1600`), 80 (`2000`), 96 (`2400`), 112 (`2800`), 128px (`3200`). — [Polaris layout tokens doc](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/design/layout/layout-tokens.mdx); [polaris-tokens `size.ts`](https://github.com/Shopify/polaris/blob/main/polaris-tokens/src/size.ts)
- Semantic space aliases: `space-card-padding` = `space-400` (16px); `space-card-gap` = `space-400` (16px); `space-table-cell-padding` = `space-150` (6px); `space-button-group-gap` = `space-200` (8px). "Always use semantic tokens over primitive ones when possible." — [polaris-tokens `space.ts`](https://github.com/Shopify/polaris/blob/main/polaris-tokens/src/themes/base/space.ts); [Polaris layout tokens doc](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/design/layout/layout-tokens.mdx)
- "The admin is high density by default, but the level of density can range depending on the merchant's task." Information-rich interfaces such as index pages or data tables "require high-density layouts for efficiency"; low density suits focused editing interfaces like a product detail page. — [Polaris: Density](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/design/layout/density.mdx)
- In high density, "use divider lines and surface colors to create clear delineation between sections"; grid and vertical divisions (made with surface colors, not lines) are "better suited for selections or data visualization." — [Polaris: Density](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/design/layout/density.mdx)
- Do not "suddenly change density in an action component"; do "split each context into its own card"; do not "mix low-density information with a high-density component in the same card." — [Polaris: Density](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/design/layout/density.mdx)
- "Space defines proximity ... the closer objects are, the stronger their perceived relationship"; "Group similar data points or tasks in the same card." — [Polaris: Layout](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/design/layout/index.mdx)
- "Use size, weight, and contrast to establish hierarchy in the admin. Divider lines are used to delimit rows of information in data and index tables, and rarely for dividing information elsewhere." — [Polaris: Layout](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/design/layout/index.mdx)
- "Software, not website": "Compact elements add detail, and larger elements command more attention"; do not contradict the importance of a task with its size. — [Polaris: Layout](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/design/layout/index.mdx)
- Nested tables: "Horizontal padding is adjusted to give more space for data"; nest a table in a card only when the card has other content; reduce border radius of inset surfaces to create a nested look. — [Polaris: Spatial organization](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/design/layout/spacial-organization.mdx)
- Card anatomy is header / body / footer; the title describes the whole card; header actions default to tertiary icon buttons; calls to action go in the footer; keep a `space-200` (8px) gap between section title and content; don't let cards become so tall they are hard to overview (offer expand/collapse). — [Polaris: Card layout pattern](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/patterns/card-layout/index.mdx)
- Index tables: numeric cells and their titles should be right-aligned and use the numeric text style; the `condensed` prop is recommended only below 490px to hide bulk actions. — [Polaris: Index table](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/components/tables/index-table.mdx)
- Data visualization: each visualization "should focus on answering a single question"; test with real data, including 1–2 points and 100+ points, sparse and spiky data; axis labels sit outside the data area; axis lines only where data appears; skip labels at regular intervals, never slant them; abbreviate y-axis values (k, b) to at most 3 numeric characters, 1 decimal, 1 letter; three-letter day and month abbreviations; comparison-to-past uses a highlight color for current and grey for past. The page carries a banner saying the section is being reworked for Polaris v12. — [Polaris: Data visualizations](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/design/data-visualizations.mdx)

Atlassian:
- Base unit `space.100` = 8px. Tokens: `space.0` 0, `.025` 2, `.050` 4, `.075` 6, `.100` 8, `.150` 12, `.200` 16, `.250` 20, `.300` 24, `.400` 32, `.500` 40, `.600` 48, `.800` 64, `.1000` 80px. — [Atlassian: Spacing](https://atlassian.design/foundations/spacing)

### Inferences
- Three independent systems land on the same numbers for product UI: 16px card padding (Polaris alias, Primer `stack-padding-normal`, Carbon grid padding), 8px for tight groups, 24px for spacious/section level. That is strong convergent evidence for a 8 / 16 / 24 core.
- Polaris's rule against mixing low-density content with a high-density component in one card argues for giving a data table its own card (or going edge-to-edge inside the card) instead of sharing a card with prose or KPIs.
- Atlassian's elevation model implies dashboard tiles should be flat (surface + border, or a surface-color step) and shadows reserved for overlays; shadows on every tile are a hierarchy cost with no grouping benefit.
- Primer's density naming is the most portable token model for a web app: the same property (gap, padding) with three named values, chosen per region.

### Gaps
- Could not confirm what the current Polaris (web components, at shopify.dev) says about density and spacing; the redirect target was not explored. React-era numbers may have changed.
- Atlassian publishes no dashboard-specific layout guidance on the pages retrieved, and I found no Atlassian compact-table typography spec or a shipped density theme (only statements that it is possible/planned).
- Primer's docs retrieved do not include a prose "density" guideline page; the guidance is from token descriptions in the primitives package (v11.10.0, which may not be the latest).
- Primer and Atlassian data-visualization guidance was not researched.

## How these systems implement density as a token, and when they recommend each mode

### Takeaway
There are three implementation patterns: a single numeric scale that subtracts 4px per step (Material/Angular Material), named size steps per component (Carbon's xs–xl rows), and named density variants of the same token (Primer's condensed/normal/spacious; Polaris's context aliases). All of them change heights, padding and gaps and leave font size alone; all recommend dense for scan-and-compare surfaces (tables, lists, filters, dashboards) and default/spacious for focused editing, touch, and prominent actions.

### Cited Findings
- Pattern 1, numeric scale: Angular Material density 0 to -5, 4px per step, clamped to a component's minimum coherent size; emitted as CSS variables by `mat.theme`. — [Angular Material theming guide](https://github.com/angular/components/blob/main/guides/theming.md)
- Pattern 2, named sizes per component: Carbon data table xs 24 / sm 32 / md 40 / lg 48 / xl 64px, with type fixed at 14px across all sizes, and toolbar/pagination matched to the row size. — [Carbon: Data table style](https://carbondesignsystem.com/components/data-table/style/); [Carbon: Data table usage](https://carbondesignsystem.com/components/data-table/usage/)
- Pattern 3, named density variants: Primer `--stack-gap-{condensed|normal|spacious}` = 8 / 16 / 24px and `--control-<size>-paddingInline-{condensed|normal|spacious}`. — [@primer/primitives 11.10.0 size.css](https://unpkg.com/@primer/primitives@11.10.0/dist/css/functional/size/size.css)
- Pattern 3b, semantic aliases: Polaris `--p-space-card-padding`, `--p-space-card-gap`, `--p-space-table-cell-padding` point at primitives, so density of a context is changed in one place. — [polaris-tokens `space.ts`](https://github.com/Shopify/polaris/blob/main/polaris-tokens/src/themes/base/space.ts)
- Layout-level density via gutters: Carbon wide 32 / narrow 16 / condensed 1px, with condensed recommended for dashboards. — [Carbon: 2x Grid usage](https://carbondesignsystem.com/elements/2x-grid/usage/)
- When dense: information-rich index pages and data tables (Polaris); "highly dense layouts where maximizing information within limited space is a priority" (Carbon xs); dense lists (Primer condensed). — [Polaris: Density](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/design/layout/density.mdx); [Carbon: Data table usage](https://carbondesignsystem.com/components/data-table/usage/); [Primer design tokens spec](https://unpkg.com/@primer/primitives@11.10.0/DESIGN_TOKENS_SPEC.md)
- When not dense: focused editing interfaces (Polaris low density); pop-up and task-based surfaces such as date pickers (Material); anything where accessibility would suffer, since density below 0 "can reduce accessibility" (Angular Material); coarse pointers need 44px targets (Primer). — [Polaris: Density](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/design/layout/density.mdx); [Angular Material theming guide](https://github.com/angular/components/blob/main/guides/theming.md); [@primer/primitives 11.10.0 size.css](https://unpkg.com/@primer/primitives@11.10.0/dist/css/functional/size/size.css)
- Keep density consistent within a component and across paired components (Carbon: same size for header and rows, consistent component sizes across a layout; Polaris: never suddenly change density inside an action component). — [Carbon: Data table usage](https://carbondesignsystem.com/components/data-table/usage/); [Polaris: Density](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/design/layout/density.mdx)
- For comparison only (outside the assigned systems, from a search summary): AWS Cloudscape ships exactly two modes, comfortable and compact, built on a 4px base unit, and warns compact can hinder readability. — [Cloudscape: Content density](https://cloudscape.design/foundation/visual-foundation/content-density/)

### Inferences
- Recommended implementation for an Angular + Tailwind app with three themes: make density orthogonal to theme. Themes set color (and possibly radius/shadow); a separate `data-density="comfortable|compact"` attribute on the root (or on a region) overrides a small set of semantic CSS custom properties. No source prescribes this exact shape; it combines Primer's naming, Polaris's aliases and Material's 4px step.
- A minimal semantic token set, with values taken from the convergent numbers above (my synthesis):

  | Token | Comfortable | Compact | Basis |
  |---|---|---|---|
  | `--space-page-x` | 24px | 16px | Primer content padding 24 at xlarge / 16 below |
  | `--space-section` (between page sections) | 32px | 24px | Atlassian large band starts at 32; Carbon `$spacing-07` |
  | `--space-card-gap` (between cards) | 16px | 8px (or 1px condensed) | Polaris card-gap 16; Carbon narrow 16 / condensed 1 |
  | `--space-card-pad` | 24px | 16px | Primer stack-padding spacious 24 / normal 16; Polaris 16 |
  | `--space-stack` (title to content in card) | 12px | 8px | Polaris 8 between section title and content |
  | `--space-inline` (icon to label) | 8px | 4px | Atlassian small band |
  | `--row-h` (table row) | 40px | 32px | Carbon md / sm |
  | `--control-h` | 36px or 40px | 32px | Primer medium 32 / large 40; Material 4px steps |
  | `--cell-pad-x` | 16px | 12px | Carbon grid padding 16; Polaris table cell 6 is tighter |

- In Tailwind v4 these can live in `@theme` as custom properties and be re-declared under `[data-density="compact"]`; utilities like `p-(--space-card-pad)` or mapped theme keys keep templates free of density conditionals. In an Angular app the attribute can be bound from a signal on the root host.
- Keep font sizes out of the density switch (Carbon precedent). If compact needs tighter text blocks, change line-height only (Carbon `body-compact-01` 14/18 vs `body-01` 14/20).
- Default to comfortable for the overall dashboard and apply compact per region (tables, filter bars), which is how Carbon mixes gutter modes and how Polaris allows high-density components inside lower-density pages.
- Exempt overlays, dialogs and date pickers from compact (Material rule), and keep at least 24px pointer targets; switch to 44px on `pointer: coarse` (Primer).

### Gaps
- No system retrieved publishes user research quantifying task performance for compact vs comfortable modes; the recommendations are stated as design rationale.
- I did not confirm how Carbon v11 or Atlassian expose a global density switch in CSS; Atlassian appears not to ship one yet.
- No system among those assigned documents a three-mode (compact / default / comfortable) user-facing toggle with values for every token; Primer's three steps are developer-facing variants, not a user setting.

## Spacing scales (4/8 pt), proximity/grouping (Gestalt), section vs intra-card spacing ratios

### Takeaway
Every system uses a 4px sub-grid with 8px as the working unit and a scale that is linear at the small end and sparse at the large end (…8, 12, 16, 24, 32, 48, 64). All ground spacing in proximity: inner spacing must be smaller than outer spacing so groups read as groups. Published values imply roughly a 1 : 2 : 4 ladder (8px within a group, 16px for card padding/between related blocks, 32px between sections); no system states an explicit ratio.

### Cited Findings
- Carbon: scale built on multiples of 2, 4 and 8; 8px mini unit. — [Carbon: Spacing](https://carbondesignsystem.com/elements/spacing/overview/); [Carbon: 2x Grid overview](https://carbondesignsystem.com/elements/2x-grid/overview/)
- Atlassian: 8px base (`space.100`), with 2, 4, 6px sub-steps and sparse large steps 32, 40, 48, 64, 80px. — [Atlassian: Spacing](https://atlassian.design/foundations/spacing)
- Polaris: 4px base (`space-100` = 4px), steps to 128px. — [Polaris layout tokens doc](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/design/layout/layout-tokens.mdx)
- Primer: 2, 4, 8, 12, 16, 24px general space tokens; 8px is "default spacing for most UI elements." — [Primer design tokens spec](https://unpkg.com/@primer/primitives@11.10.0/DESIGN_TOKENS_SPEC.md)
- Material: density steps are 4px. — [Angular Material theming guide](https://github.com/angular/components/blob/main/guides/theming.md)
- Proximity stated as the governing principle: Polaris ("the closer objects are, the stronger their perceived relationship"), Atlassian ("elements placed close together are assumed to be related"), Carbon (closer elements read as more related; space can group content without dividers), Apple (group with negative space, container shapes, or separator lines). — [Polaris: Layout](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/design/layout/index.mdx); [Atlassian: Spacing](https://atlassian.design/foundations/spacing); [Carbon: Spacing](https://carbondesignsystem.com/elements/spacing/overview/); [Apple HIG: Layout](https://developer.apple.com/design/human-interface-guidelines/layout)
- Space as hierarchy: more surrounding space signals higher importance (Carbon); varying whitespace separates an element to give it more importance (Atlassian). — [Carbon: Spacing](https://carbondesignsystem.com/elements/spacing/overview/); [Atlassian: Spacing](https://atlassian.design/foundations/spacing)
- Rhythm: repeated spacing signals equal weight (Carbon, Atlassian). — [Carbon: Spacing](https://carbondesignsystem.com/elements/spacing/overview/); [Atlassian: Spacing](https://atlassian.design/foundations/spacing)
- Dividers are a last resort outside tables: Polaris reserves divider lines for data and index tables and uses surface color and nesting elsewhere; Atlassian prefers borders or whitespace over elevation for grouping. — [Polaris: Spatial organization](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/design/layout/spacial-organization.mdx); [Atlassian: Elevation](https://atlassian.design/foundations/elevation)
- Published inner vs outer values: Polaris title-to-content 8px, card padding 16px, card gap 16px; Atlassian within cards 0–8px, between card elements 12–24px, between page sections 32–80px; Primer stack gap 8 / 16 / 24px; Carbon box padding 16px with gutters 32 / 16 / 1px; Material codelab pane padding 16dp with 24dp between cards. — [Polaris: Card layout pattern](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/patterns/card-layout/index.mdx); [polaris-tokens `space.ts`](https://github.com/Shopify/polaris/blob/main/polaris-tokens/src/themes/base/space.ts); [Atlassian: Spacing](https://atlassian.design/foundations/spacing); [@primer/primitives 11.10.0 size.css](https://unpkg.com/@primer/primitives@11.10.0/dist/css/functional/size/size.css); [Carbon: 2x Grid usage](https://carbondesignsystem.com/elements/2x-grid/usage/); [Design an Adaptive Layout with Material Design (codelab)](https://developer.android.com/codelabs/adaptive-material-guidance)
- White space on dashboards is used to group or separate and to show priority (Carbon dashboards page, which also cites a roughly 20 percent comprehension improvement). — [Carbon: Dashboards](https://carbondesignsystem.com/data-visualization/dashboards/)

### Inferences
- Working rule derived from the values above: spacing should increase with each level of the containment hierarchy, roughly doubling: 4px (icon to label) → 8px (items within a group, title to content) → 16px (card padding, between sub-groups) → 24–32px (between sections). An inner gap should never equal or exceed the gap that separates its parent from siblings, or the grouping reads ambiguously.
- The systems disagree on whether the gap between cards should be larger or smaller than card padding: Material's codelab uses 24 between and 16 inside; Polaris uses 16 and 16; Carbon's condensed mode uses 1px between and 16 inside. The disagreement resolves by how grouping is drawn: when cards have a visible container (border or surface step), the container does the grouping and the gap can shrink to 8–16px or even 1px; when grouping relies on white space alone, the gap must exceed inner padding.
- For an "airy" dashboard, the cheapest gains consistent with these systems are: larger card padding (24px), fewer and flatter containers, one clearly larger gap between sections (32px+) than between cards (16px), and extra space around the KPI band to mark it as most important. Uniformly inflating every gap removes the hierarchy that proximity is supposed to carry.
- A Tailwind spacing scale restricted to 1, 2, 3, 4, 6, 8, 12, 16 (4, 8, 12, 16, 24, 32, 48, 64px) covers every value cited above except Atlassian's 6px and 20px steps.

### Gaps
- No system retrieved states an explicit numeric ratio between section spacing and intra-card spacing; the 1 : 2 : 4 ladder is derived from token values and usage bands.
- None of the systems name "Gestalt" explicitly in the passages retrieved (they say "proximity", "similarity", "rhythm"); attributing the guidance to Gestalt theory is an interpretation.
- The research behind Carbon's "almost 20 percent" comprehension claim was not traced to a primary study.
- No guidance was found on vertical rhythm/baseline grids for dashboards, or on maximum content width for analytics layouts beyond Primer's 1280px full-page cap.
